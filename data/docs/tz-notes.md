# Аналіз технічного завдання Student Assistant

## Функціональні вимоги

Застосунок Student Assistant призначений для керування навчальними завданнями студента.

Основні функції, які повинні бути доступні клієнтам:
- перегляд переліку навчальних завдань;
- додавання нового завдання із зазначенням назви, дедлайну та пріоритету;
- позначення завдання як виконаного або невиконаного;
- редагування завдання;
- видалення завдання;
- фільтрація або сортування завдань за станом виконання чи пріоритетом.

Фільтрація та сортування визначені як бажана вимога, тому вони не є обов'язковими для кожного окремого клієнта.

## Нефункціональні вимоги

- система повинна бути кросплатформною;
- сукупність клієнтських модулів має покривати Windows, macOS та Linux;
- клієнтські модулі мають бути незалежно розгортуваними;
- клієнти не повинні мати прямих залежностей один від одного;
- взаємодія між клієнтами здійснюється через спільний файл даних;
- розробка та ведення історії змін здійснюються через Git і GitHub;
- для кожної задачі використовується окрема гілка, Pull Request та рецензування коду;
- репозиторій повинен містити README.md з описом призначення проєкту, архітектури, технологій та структури директорій;
- аналіз технічного завдання зберігається у файлі docs/tz-notes.md.

## Модулі та технології

| Модуль | Технологія | Призначення |
|---|---|---|
| Веб-клієнт | React | Реалізація веб-інтерфейсу з адаптивною версткою |
| Десктопний контейнер | Electron або NW.js | Обгортання веб-інтерфейсу у десктопний застосунок |
| Нативний десктопний клієнт | C++ / Qt | Реалізація нативного клієнта |
| Аналітичний модуль | Python / Flet | Реалізація аналітичного модуля |

Усі чотири модулі працюють зі спільним файлом data/tasks.json та не повинні мати прямих залежностей один від одного.

## Формат обміну даними

Для обміну даними між клієнтськими модулями використовується єдиний файл:

`data/tasks.json`

Кожне навчальне завдання представлено JSON-об'єктом із такими полями:
- `id` — унікальний числовий ідентифікатор;
- `title` — назва завдання;
- `completed` — логічне значення `true` або `false`, яке визначає стан виконання;
- `dueDate` — дата у форматі `РРРР-ММ-ДД`;
- `priority` — пріоритет завдання: `low`, `medium` або `high`.

Перелік і призначення полів не повинні змінюватися окремими клієнтами без узгодження зі спільним форматом.

## Відкриті питання

- Чи є фільтрація та сортування обов'язковими для веб-клієнта, чи вони залишаються лише бажаною функцією?
- Який саме варіант десктопного контейнера буде використовуватися в проєкті: Electron чи NW.js?
- Який мінімальний набір функцій повинен мати кожен окремий клієнт, якщо частина функцій визначена як бажана?
- Які саме аналітичні можливості повинен реалізувати модуль Python / Flet?
- Які критерії та сценарії повинні використовуватися під час інтеграційного тестування всіх клієнтських модулів?
